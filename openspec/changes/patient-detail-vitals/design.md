## Context

app 目前只能列出病人與數出人數。點進病人沒有反應，而臨床上真正要看的變化趨勢一樣也還沒做。

seed 資料已備妥每位病人 48 小時、四種生命徵象的時序（體溫、心跳、呼吸帶 server 提供的參考範圍；血氧刻意不帶）。第一次要在畫面上處理「時間軸」與「參考範圍」這兩件事。

已知的 server 陷阱兩項會直接影響這個 change：`Observation?date=` 在 Siming 上宣稱支援卻無效；`_sort` 只認五個欄位且未知欄位靜默丟棄，`-date` 不在其中。

## Goals / Non-Goals

**Goals:**

- 一位病人的生命徵象變化在一眼之內看得出來
- server 提供的參考範圍看得見，但不對任何一點下判斷
- 清單與詳情的往返不丟失使用者的位置

**Non-Goals:**

- 不做寫入、不做其他資料區塊（用藥、檢驗、診斷）
- 不做時間範圍切換
- 不標記異常、不提示嚴重程度、不建議行動
- 不快取觀測值

## Decisions

### 排序必須在 client 端做

`Observation?_sort=-date` 在 Siming 上不會報錯，也不會生效——`_sort` 的白名單只有五個欄位，`date` 不在裡面，而未知欄位是**靜默丟棄**的。

折線圖依賴點的順序：順序錯了，畫出來是一團亂線，而且看起來像資料有問題而不是排序有問題。所以 client 端一律依 `effective` 時間重新排序，不管 server 回傳的順序。

這與先前「UI 宣告的範圍必須由 client 守住」是同一條原則的延伸：**凡是畫面的正確性依賴某個性質，那個性質就得由 client 保證**，server 的查詢參數只是最佳化。

### 參考範圍畫成區間帶，不對個別點著色

`RuleMark` 或 `RectangleMark` 畫出 server 提供的上下界，讓讀者自己看到值落在哪裡。

**不做**的是：把超出範圍的點塗紅、加驚嘆號、或標任何文字。理由不是美感——那條線分隔的是「呈現事實」與「臨床判讀」，而後者會把這個產品推向醫材的分類。區間帶是 server 給的界限，畫出來是轉述；把某一點宣告為異常則是我們在下判斷。

沒有參考範圍的項目（例如 seed 裡的血氧）就不畫帶子，也不套用任何內建值。

### 每種生命徵象一張獨立的圖

不疊在同一張圖上。體溫 36–39、心跳 60–120、血氧 89–99 的量級與單位都不同，疊起來需要多重 Y 軸，讀起來比分開更費力。

每張圖各自帶自己的單位標籤與參考範圍。

### 詳情頁的資料以 primitive 傳入，觀測值自己查

`PatientDetailHostController` 接收 patient id、顯示名稱、性別、年齡、病歷號——全部是 primitive。不接收 `PatientListViewModel.Patient`。

身分資料由清單傳入而非重查，是因為清單已經有了，重查一次只會讓畫面先空白再填上。而觀測值必須自己查——清單沒有那份資料。

### 導航沿用內容區的 NavigationStack

從清單 push 詳情，與「grid → 清單」同一個堆疊。返回時 SwiftUI 保留清單的 state（切片、關鍵字、捲動位置），不需要額外處理。

## Implementation Contract

**行為**

- 病人清單的列可點擊，開啟該病人的詳情
- 詳情頁上半顯示身分資料，下半依生命徵象種類分別呈現趨勢圖
- 每張圖的點依時間排序，橫軸為時間、縱軸為數值，標註單位
- server 有提供參考範圍的種類，圖上畫出該範圍的區間帶；沒有的就不畫
- 任何一點都不因落在範圍外而改變外觀
- 觀測值載入中／無資料／失敗／有內容四態各自可辨，且失敗不清除已顯示的圖
- 返回清單後，切片與關鍵字維持原樣

**介面與資料形狀**

- `PatientDetailHostController` 的建構參數全為 primitive（id、名稱、性別字串、年齡、病歷號）加上共用的 `FHIRClient`
- ViewModel 的 State 以「種類 → 該種類的時序」組織，每個種類帶自己的單位與參考範圍
- 排序在 DTO 轉 Domain Model 時完成，View 不負責排序
- 觀測值缺少數值或時間時於轉換階段濾除，不進入 State

**失敗模式**

- 觀測值查詢失敗且畫面已有圖 → 保留圖，另外呈現失敗
- 觀測值查詢失敗且畫面無圖 → 顯示失敗與重試
- 某種類的觀測值全部缺少數值或時間 → 該種類不出現，不畫空圖
- 病人沒有任何觀測值 → 明確說明沒有紀錄，與載入中及失敗都不同

**驗收準則**

- ViewModel 測試涵蓋：亂序回應被排序、缺值缺時間被濾除、單點仍成立、無資料與失敗四態、有內容時失敗不清空
- 參考範圍的存在與否分別有測試，確認沒有範圍時不會出現任何內建值
- 模擬器實跑截圖：對 seed 的病人（含有超出參考範圍值的那三位）確認圖上看得到區間帶，且該點外觀與其他點相同
- 文案複查：詳情頁全部字串不含異常、偏高、偏低、疑似、需注意、建議等判讀用語
- 中英文各截圖一次

**範圍邊界**

- 範圍內：`PatientDetail` 新 feature、`PatientList` 的列選取與導航、`FHIRSearch` 的觀測值查詢調整與測試、`FHIRCore` 的時間工具、字串 catalog
- 範圍外：寫入路徑、其他資料區塊、時間範圍切換、主畫面的 grid 與計數、Siming 或 seed 的改動

## Risks / Trade-offs

- **Swift Charts 的區間帶在深色模式下可能與背景對比不足** → 用語意色彩並在兩種外觀下各看一次
- **48 小時內若某病人只有一兩點，圖看起來很空** → 單點仍渲染為點；這是資料的事實，不用假造中間值填滿
- **不對超出範圍的點著色，可能被認為「少了功能」** → 這是刻意的取捨，理由寫在 spec 的 requirement 裡；未來若要加，也只能由 server 提供的 interpretation 欄位驅動，不能由 app 判斷
- **`_sort` 失效是靜默的，未來換 server 可能誤以為排序有效** → client 端一律重新排序，不論 server 行為

## Migration Plan

無資料遷移，無持久化格式變更。

回退為還原本 change 的 commit；病人清單會回到不可點擊的狀態。

## Open Questions

- 縱軸是否該固定為參考範圍的合理外擴（讓不同病人的同一種圖可比較），或依該病人的實際數值自動縮放。自動縮放會讓小幅波動看起來很劇烈，固定範圍則可能把極端值切掉。先採自動縮放，看實際資料再調。
- 觀測值若帶 `interpretation` 欄位（server 自己的判讀），是否呈現。那是 server 的判斷不是我們的，理論上可以轉述；但 seed 沒有這個欄位，真實 server 的填寫品質也未知，暫不處理。
