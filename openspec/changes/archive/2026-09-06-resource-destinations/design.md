## Context

四張切片卡片（全部病人／今日就診／超出參考值／用藥中）目前**都**導向同一份病人清單，而清單的每一列都導向同一個生命徵象詳情頁。切片只影響查詢條件，不影響抵達之後看到什麼。

後果是：按「超出參考值 3」得到的三列，與按「全部病人」得到的列**完全相同**（姓名、性別、年齡、病歷號）。使用者必須自己記住剛才按了哪一張卡片。

更根本的是資訊架構上的錯位：有兩張卡片的主角不是病人。「用藥中」算的是有在用藥的**病人數**，但整個 app 沒有任何地方看得到藥；「超出參考值」的主角是**數值**。拿病人清單回答「哪些數值動了」，形狀本身就不對。

本案的目標與先前「保持簡單、砍到只剩一件事」的方向不同，理由寫在 proposal：這個 repo 的定位已確定是能力證據而非產品，而證據的判準是涵蓋面。

## Goals / Non-Goals

**Goals:**

- 四張卡片各自走到一個真正不同的終點頁，每一頁對應一個 FHIR resource 家族
- 每一頁展示該 resource 家族**真正不好處理**的地方，而不只是把欄位印出來
- seed 提供足以展示那些難處的資料——尤其是「記錄本身沒有把話講完」的情況
- 維持唯讀與不做臨床判讀的界線

**Non-Goals:**

- 不新增第五張卡片
- 不做編輯模式與收費閘門
- 不做 `MedicationAdministration`、給藥核對或任何寫入
- 不做給藥時間表展開、提醒、交互作用檢查
- 不改動現有的生命徵象詳情頁

## Decisions

### 終點頁由抵達的切片決定，而不是由病人決定

同一位病人，從不同卡片點進去會看到不同的畫面。這乍看違反直覺（同一個人為什麼有四個詳情頁），但**切片就是使用者的提問**：從「用藥中」進來的人問的是藥，從「超出參考值」進來的人問的是數值。忽略那個提問、永遠給同一頁，等於把使用者的意圖丟掉。

替代方案是做一個帶四個分頁的病人詳情頁。否決的理由是它把「四個 resource 家族各自被正確處理」這件事藏進分頁列——證據要看得見才算證據；而且分頁頁面會讓每一頁都變成清單的附屬品，弱化了「主角不是病人」那兩張卡片的重點。

切片已經在清單的 state 裡，分流是既有結構的延伸。

### 時程照實呈現，絕不展開成具體時間

`dosageInstruction.timing` 說「一天三次」時，它**沒有**說是哪三次。那三個時間點由機構的給藥常規決定，不存在於 FHIR 資料裡。

因此畫面必須能表達「記錄沒有指定時間」這件事本身，而不是留白、也不是填上 08:00／16:00／24:00。填上去等於把假設當成處方呈現——那是本案最主要的一條臨床紅線，也是這一頁最值得展示的判斷。

`NIS-TECH-SPEC.md` §5.4 早已記下這個坑；本案是第一次讓它出現在畫面上。

### 開放式 period 代表進行中，不用當下時間替代

只有 `start` 沒有 `end` 的 `Encounter.period`，在 FHIR 裡代表就診尚未結束或結束時間未被記錄。畫面呈現為「進行中」，不顯示結束時間，也不以當下時間替代。

替代會斷言記錄沒說的事。這個語意在 demo-data 那輪已經被理解過（開放式 period 會被 `date=ge<未來>` 命中），本案讓它在畫面上被看見。

同時：`status` 與 `period` 是兩個獨立的事實，可能互相矛盾。顯示的是記錄的 `status`，不從 period 推導。

### identifier 依型別分辨，無法辨識就不顯示

`Patient.identifier` 是一個陣列，裡面可能同時有病歷號、身分證號、以及灌資料用的內部 key。既有的 `medicalRecordNumber` 已經只採用標記為 MR 的那一個——本案把同樣的原則套到身分證，並確立通則：**辨識不出用途的 identifier 不顯示**。

理由是一個沒有標籤的號碼會讓讀的人自己假設它是他認得的那一個。這個 bug 在 demo-data 那輪發生過（病歷號欄位顯示的是 server 內部識別碼）。

### 三頁共用一種「取這個病人的某類資源」的查詢形狀

三個新頁面都是「以 patient 為條件取一類資源、依時間排序」。查詢建構集中在既有的 `FHIRSearch`，與現有的具名查詢並列，不各自散寫。

排序一律在 client 端做，理由與既有的一致：server 的 `_sort` 只認五個欄位且未知欄位靜默丟棄。

## Implementation Contract

#### 種子資料（`demo-data`）

**行為**：seed 產生的處方涵蓋四種 dosage 形態——(a) 一天三次無指定時間、(b) 需要時服用、(c) 多段遞減劑量、(d) 一天兩次帶明確時間。每種至少一筆。其餘既有性質不變：處方只由具處方權者開立、重跑冪等。

**驗收**：重灌後查詢 `MedicationRequest`，斷言四種形態各自存在——存在無 `timeOfDay` 的 `timing.repeat`、存在 `asNeeded`、存在 `dosageInstruction` 陣列長度大於一且劑量相異、存在帶 `timeOfDay` 的 `timing.repeat`。

**範圍界線**：只擴充 `dosageInstruction`，不改動病人、就診、觀測值的產生方式。

#### 導航（`patient-list`）

**行為**：清單的列被選取時，開啟的畫面由清單所屬的切片決定。四個切片對應四個終點，傳遞的仍只有 primitive。

**失敗模式**：切片識別字串無法對應到已知切片時，導向病歷頁（Patient 是四者中最基本、對任何病人都成立的那一個），不是崩潰也不是空白。

**驗收**：TidengTests 對四個切片各斷言一次開啟的目的地型別；並斷言傳入的是 primitive。

#### 病歷頁（`patient-record`）

**行為**：顯示姓名、性別、生日與推算年齡、病歷號、身分證號。任一欄位缺漏即整行省略。identifier 依 type coding 分辨，辨識不出的不顯示。

**驗收**：TidengTests 注入三種 Patient——欄位齊全、無生日、identifier 只有內部 key——分別斷言顯示內容與省略行為。

#### 就診頁（`encounter-status`）

**行為**：列出該病人的就診，依開始時間新到舊。每筆顯示 status、class、開始時間；有 `period.end` 時顯示結束時間，沒有時顯示為進行中；完全沒有 period 時兩者皆不顯示且不宣稱進行中。participant 解析為 practitioner 姓名，解析不到時顯示 reference 且不影響該筆顯示。

**失敗模式**：practitioner 查詢失敗不得使整頁失敗——與既有身分解析的降級一致。

**驗收**：TidengTests 涵蓋四種 period 形態（有頭有尾、只有頭、完全沒有、status 與 period 矛盾）與 participant 解析失敗，斷言各自的呈現。

#### 用藥頁（`medication-list`）

**行為**：列出該病人的處方，每筆顯示藥品、status、requester，以及**每一段** `dosageInstruction`。時程呈現規則：

- `timing.repeat` 有 `timeOfDay` → 顯示那些時間
- `timing.repeat` 有 frequency／period 但無 `timeOfDay` → 顯示次數與週期，並**明確表示未指定時間**
- `asNeeded` → 顯示為需要時服用，不呈現任何時程
- 完全沒有 `dosageInstruction` → 只顯示藥品，不顯示劑量行

**失敗模式**：無法解讀的 timing 結構顯示為「未指定」而非留白——留白會被讀成「沒有時程」，那與「有時程但我們看不懂」是不同的事。

**驗收**：TidengTests 對四種 dosage 形態各注入一筆，斷言畫面文字包含該有的、且**不包含任何具體時間**（無 `timeOfDay` 的那筆）。另斷言多段 `dosageInstruction` 全部出現且順序不變。

#### 全頁共通

**行為**：三個新頁面各自具備載入中、成功有內容、成功無內容、失敗四種狀態，且已有內容時失敗不清空——與既有清單一致。

**範圍界線**：新增三個 Pages 目錄與對應的查詢；不動生命徵象詳情頁、不動切片計數、不動登入流程。

## Risks / Trade-offs

- **同一位病人有四個終點頁，可能讓人困惑「哪一個才是這個病人的頁面」** → 每一頁的標題明確說明它在看什麼；且四者皆由卡片抵達，使用者是帶著問題進來的
- **「未指定時間」的文案很容易被寫成判讀**（例如「需確認給藥時間」）→ 文案只陳述記錄狀態；驗收包含逐字檢查新增字串
- **三個新頁面等於三倍的四態處理** → 四態的形狀已在既有頁面確立，照抄同一種結構，不各自發明
- **證據的價值取決於每一頁都紮實** → 每一頁的驗收都指定了「難的那個情況」，而不只是 happy path

## Open Questions

- 就診頁是否要顯示 `Encounter.reasonCode`（就診原因）。它是很有用的資訊，但診斷碼的呈現離「陳述事實」與「判讀」的界線很近——本案不做，待畫面出來後再評估。
